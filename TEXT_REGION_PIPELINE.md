# Text Region Pipeline

## Purpose and boundary

This pipeline locates visible text-like regions so visual measurements can be taken from those pixels. It is not an OCR or document-understanding pipeline. Localization identifies where a region is; it does not establish image authenticity and does not provide a semantic signal.

## Stage contract

```text
decoded image
  -> deterministic image preparation
  -> detector backend
  -> normalized geometry validation
  -> crop or mask generation
  -> region quality record
```

Input: one decoded image and a fixed detector configuration.

Output: zero or more TextRegion records, region crops or masks, a detection status, quality flags, and a detector configuration hash.

## Detector adapter

The detector must implement the interface in ARCHITECTURE.md. The backend is configurable because the thesis has not fixed one detector. A feasibility gate must select one backend for a final experiment and record:

- backend name and version;
- model weights identifier and checksum, when applicable;
- input preprocessing;
- confidence threshold;
- non-maximum suppression or grouping settings;
- output geometry type;
- detector runtime and hardware context;
- representative localization review result.

The initial implementation must include:

1. one production adapter selected through the feasibility gate; and
2. a deterministic fixture adapter for unit and integration tests.

The fixture adapter must never be used to report thesis results.

## Text semantics prohibition

Some detector libraries return recognized text, language, or OCR confidence together with geometry. The adapter must discard those values immediately. It may retain only:

- region coordinates or polygon points;
- detector confidence if it is a localization confidence and is explicitly treated as metadata;
- region ordering or IDs generated by the adapter;
- geometry and processing status.

The following must never enter TextRegion, feature extraction, split grouping, model fitting, or the UI result:

- recognized characters or words;
- spelling or language;
- merchant, amount, date, or other receipt content;
- semantic embeddings or text categories;
- OCR text confidence used as a class signal.

## Coordinate normalization

Store geometry in both pixel and normalized form when available. Normalized coordinates use the original decoded image dimensions:

```text
x_norm = x_pixel / image_width
y_norm = y_pixel / image_height
```

For a rectangle, require 0 <= x1 < x2 <= 1 and 0 <= y1 < y2 <= 1 after clipping. For polygons, require at least three valid points and a positive area. Preserve the unclipped geometry in a diagnostic record only if it contains no semantic data; record that clipping occurred.

Each region receives a deterministic region_id based on the sample ID and stable geometry order. Do not use recognized text as an ID.

## Detection preprocessing

The preprocessing order must be fixed and recorded:

1. decode the file without changing the original bytes;
2. convert to the detector's required color representation;
3. resize only according to the configured policy while preserving aspect ratio;
4. run the detector;
5. map geometry back to original-image coordinates;
6. validate and clip geometry;
7. generate crops or masks for feature extraction.

The detector preprocessing is separate from feature preprocessing. Do not use the test split to choose a resize or threshold.

## Crop and mask policy

Prototype defaults:

- use a small configurable relative padding around rectangular boxes;
- preserve the original crop aspect ratio;
- record the crop coordinates and output dimensions;
- use a mask or polygon-aware crop when the selected detector provides valid polygons;
- do not rotate regions based on recognized text orientation; use geometry-only orientation if the detector supplies it;
- avoid aggressive smoothing, sharpening, or compression before feature extraction.

The final configuration must state whether feature values use the complete padded crop, a polygon mask, or both. The same policy applies to both labels.

## Detection quality checks

For development images, inspect overlays for:

- missed visible text;
- boxes that cut through text;
- excessive background;
- duplicate or overlapping detections;
- false positives on nontext objects;
- sensitivity to receipt orientation and scale.

After the detector configuration is fixed, the final test labels must not be used to revise it. The review produces localization_review.json and a representative overlay set.

## No-detection policy

No detections is a valid pipeline state, not an implicit success or failure. The default behavior is:

```text
region_count = 0
no_detection = true
all region aggregate values = missing according to feature schema
quality_flags += ["no_detection"]
```

The downstream preprocessing pipeline must either:

- retain the image with training-fitted imputation plus a no-detection indicator; or
- exclude it under a predeclared dataset rule and include it in the exclusion report.

The choice must be fixed before final test evaluation and applied equally to both labels.

## Failure handling

| Condition | Status | Behavior |
|---|---|---|
| Image cannot decode | decode_failed | Do not create a feature row; record the file and error. |
| Detector unavailable | detector_unavailable | Stop the run; do not silently fall back to a different backend. |
| Detector returns no regions | no_detection | Create an explicit no-detection record. |
| Region coordinates invalid | invalid_geometry | Drop the invalid region, retain the image status, and fail the run if no valid regions remain unless the configured policy permits no detection. |
| All regions are too small | insufficient_region_area | Retain a quality flag and apply the declared no-detection policy. |
| Region count exceeds configured limit | region_limit_exceeded | Apply deterministic ordering and truncation only if predeclared; otherwise fail the image record. |
| Third-party output includes text | semantic_output_discarded | Discard text fields and continue only with geometry. Record the event without storing the text. |

## Artifact format

Per-image localization JSON:

```json
{
  "schema_version": "localization-1",
  "sample_id": "sample-0001",
  "image_sha256": "...",
  "image_width": 1200,
  "image_height": 1600,
  "detector": {
    "name": "configured-backend",
    "version": "...",
    "config_sha256": "..."
  },
  "status": "ok",
  "regions": [
    {
      "region_id": "sample-0001-r000",
      "bbox_px": [100, 200, 800, 260],
      "bbox_norm": [0.083333, 0.125, 0.666667, 0.1625],
      "polygon_norm": null,
      "confidence": 0.91,
      "crop_path": "artifacts/localization/sample-0001-r000.png",
      "quality_flags": []
    }
  ],
  "warnings": []
}
```

The example is a schema example only. It is not a measured thesis result and does not prescribe a detector or threshold.

## Acceptance criteria

- A detector adapter returns only validated geometry and nonsemantic metadata.
- The same detector configuration runs on both classes.
- Overlay artifacts can be generated without showing or storing recognized text.
- No-detection and invalid-region cases are explicit and testable.
- Region order and IDs are deterministic for the same input and configuration.
- A changed detector setting creates a new configuration hash and cannot silently reuse old features.
- The final feature matrix can be traced back to the localization artifact for every image.
